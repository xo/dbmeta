# D204. Redshift answers the grants and the roles, and takes every password

Status: Amends D182.

## The decision

Ken said on 2026-10-09 to finish anything for Redshift. This decision records
what the second run against Redshift Serverless 1.0.434008 in us-east-1 found
and what changed. The model answers 18 of the 65 questions, where it answered
11.

Redshift has a conformance target now, and the conformance and parity files
hold its sections. The statement that sets a password ran against a user that
the test makes, and it needed no change. Every statement was timed against a
catalog of 2,000 tables and views, 8,500 columns and 1,999 constraints.

## What the model reads now

Seven kinds are new.

1. Privileges reads the ACL of pg_class. Every user reads it in full. It lists
   a grant to a user and to a group. It does not list a grant to a role.
2. Column privileges reads SVV_COLUMN_PRIVILEGES. pg_attribute has no ACL.
3. Role grants joins SVV_USER_GRANTS, SVV_ROLE_GRANTS and the members of
   pg_group. The grantor is absent, because no view records it.
4. Default ACLs reads pg_default_acl.
5. Languages reads pg_language and finds the handler by name in pg_proc,
   because the regprocedure cast is not there.
6. Settings reads pg_settings and current_setting.
7. Constraint columns reads the key arrays of pg_constraint. Redshift 8.0 has
   no unnest, so a series of 32 positions stands in for it.

Two kinds changed.

- Roles lists a user, a group from pg_group and a role from SVV_ROLES. A group
  and a role cannot log in. The connection limit and the roles of a user are
  still not read, because SVV_USER_INFO and SVV_USER_GRANTS show a user only
  its own rows. Role grants answers the second one.
- Columns reads the collation from SVV_COLUMNS and reports the identity kind d.

The fixture builds two roles, a grant of one to the other, a group, a table
grant, a column grant and a default grant, and its teardown removes them. A
test reads each kind back as typed values.

## What the server answered

A column with IDENTITY(1, 1) or GENERATED ALWAYS AS IDENTITY has the default
`"identity"(<oid>, 0, '1,1'::text)`, and an INSERT of a value fails with
"cannot set an identity column to a value". The flag a was right. A column
with GENERATED BY DEFAULT AS IDENTITY has the default
`default_identity(<oid>, 0, '5,2'::text)` and accepts a value. It reports d.

The collation of a column is case_sensitive or case_insensitive in
SVV_COLUMNS, and it is absent for a column that is not a character type. A
subquery on SVV_COLUMNS fails with "plan should not reference subplan's
variable", so the statement joins it. A comment on a column and a default
read as they were written. Redshift refuses GENERATED ALWAYS AS (expression)
and refuses a CHECK constraint, so the generated field stays absent and the
conformance section has no check line.

The SVV views filter by user. A user reads only its own rows of
SVV_USER_GRANTS, SVV_ROLE_GRANTS, SVV_USER_INFO and SVV_ALL_TABLES. It reads
only the grants that name it in SVV_COLUMN_PRIVILEGES and
SVV_RELATION_PRIVILEGES. SVV_ROLES and pg_group show everybody the same rows.

## What the password test found

The documentation says that a password cannot hold a single quote, a double
quote, a backslash, a slash, an at sign or a space. The server accepts all of
them, and a login with each one works. It also accepts 65 characters. It
refuses a password of fewer than 8 characters, and one with no digit, no upper
case letter or no lower case letter, and it says which in words.

So `ChangePassword` refuses nothing. D56 and Oracle refuse a character that a
quoted identifier cannot hold, and Redshift has no such character, because its
literal escapes a quote by doubling it and a backslash by doubling it. The test
runs the seven hostile passwords of D127 with the prefix Aa1-, because one of them has 7 characters, and eight more: a slash, an at sign,
a space, a percent sign, dollar signs, every punctuation mark, 64 characters
and 65 characters. It runs on a user named dbmeta_pw that it makes and drops.
It never changes the administrator.

## What parity found

The three principals read the same rows as the administrator for privileges,
roles, default ACLs, languages, settings, constraint columns and every kind
D182 measured. Two kinds read fewer rows, and both are the SVV filter.

- Role grants reads fewer rows for the owner, the grantee and the stranger.
  Each one sees only its own grants.
- Column privileges reads fewer rows for the grantee and the stranger.

The statements work for a user that is not the administrator. They report only
what that user can see, and no statement is refused.

## What conformance found

Redshift agrees with the other relational databases on 23 lines, and it is not
in `agreementExcluded`. It differs from PostgreSQL on three lines. The fixture
gives book.book_id and shipment.shipment_id no default, where PostgreSQL's
fixture uses serial. Redshift has no CHECK constraint, so it has no check
line. Neither difference is a fault.

## What it costs

D47 asks for every statement against a catalog with thousands of tables. The
scratch schema held 1,500 tables with 5 columns each, 500 views, 499 foreign
keys and 1,500 primary keys. It took 30 seconds to build with a stored
procedure. Each statement ran once.

| Statement | Empty | 2,000 relations |
| --- | --- | --- |
| tables | 0.85 s | 1.6 s for 2,000 rows |
| columns | 0.57 s | 3.1 s for 8,500 rows |
| columns without the collation join | 0.54 s | 2.1 s for 8,500 rows |
| constraints | 0.56 s | 1.1 s for 1,999 rows |
| constraint columns | 0.58 s | 1.0 s for 1,999 rows |
| privileges | 0.54 s | 0.5 s for 2,000 rows |
| views | 0.54 s | 0.6 s for 500 rows |
| every other statement | 0.5 to 1.3 s | 0.5 to 1.3 s |

Half a second is the round trip. A statement that matches no schema takes the
same time on the big catalog as on the empty one, so no statement scans more
than the rows it returns, and the collation join costs about one second for
8,500 columns. Column privileges and role grants read an SVV view of the grants
and not the catalog, and the scratch schema held none, so they are not shown
against many grants.

## What this left out

- Spectrum. `CREATE EXTERNAL SCHEMA` fails with "Cannot find default IAM role
  on this cluster". The namespace has no IAM role. On the empty catalog
  SVV_EXTERNAL_SCHEMAS, SVV_EXTERNAL_TABLES, SVV_EXTERNAL_COLUMNS,
  SVV_EXTERNAL_DATABASES and SVV_DATASHARES return no row. The fixture makes no
  external table, and no kind reads one.
- A grant to a role in Privileges. Only SVV_RELATION_PRIVILEGES lists it, and
  that view shows a user only the rows that name it.
- The connection limit and the roles of a user in Roles, for the same reason.
- The routine parameters, types, casts, aggregates, operators, conversions,
  column statistics and row level security policies. Each has a source and none
  is read. They are in `docs/BACKLOG.md`.
- A collation kind. Redshift has two fixed collations and no list of them.

## How it was asked

Gemini and DeepSeek sorted the unanswered kinds, as rule 14 asks. Both named the
SVV views that hold the grants, the roles, the external tables and the
datashares. DeepSeek also named SVV_COLLATIONS, SVV_SEQUENCES, SVV_POLICIES and
SVV_CONSTRAINT_COLUMNS, and none of them exists. Every lead was run on the
server.

The work used 12 runs of dbrun in all. Two of them read only the version.
